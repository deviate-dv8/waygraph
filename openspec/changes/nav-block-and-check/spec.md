# nav-block-and-check Specification

## Purpose
Separates "navigate to a URL" from "act on the current page" as a structural,
engine-enforced distinction, so a Block's own type signals whether it can navigate at all.
This is the foundation a later page-recognition/planning layer needs to reason over the
Block library reliably - see the parent proposal's autonomous-mode motivation.

## Requirements

### Requirement: NavBlock is a distinct Block that only navigates
A NavBlock SHALL be created via `defineNavBlock(...)`, SHALL extend `Block` (usable
anywhere a `Block` is - `defineFlow`, `connect`, `composeBlock` - without special-casing),
and SHALL have no free-form `act()` of its own. Its `act()` SHALL always be exactly
`page.goto(url)` plus normal engine plumbing, generated by the engine - never authored.

#### Scenario: A NavBlock's act() navigates and nothing else
- **WHEN** a NavBlock is defined as `defineNavBlock({ name: "nav-web-login", url: "/login" })`
- **THEN** running it SHALL navigate the page to `/login`
- **THEN** the definition SHALL NOT accept any other action code for `act()`

#### Scenario: A NavBlock drops into an existing Flow like any Block
- **WHEN** a NavBlock is placed inside `defineFlow([start, navBlock, actionBlock, end])`
- **THEN** it SHALL typecheck and run exactly as any other `Block<In,Out>` would in that
  position, with no special-casing in `defineFlow`, `connect`, or `composeBlock`

### Requirement: A NavBlock's URL may depend on mem
NavBlock's `url` SHALL accept either a plain string or a function
`(mem: MemPage) => string`, so a parameterized route (e.g. `/dashboard/requests/:id` with
a real id read from mem) can be expressed without falling back to a free-form Block.

#### Scenario: A parameterized route is resolved from mem at run time
- **WHEN** a NavBlock is defined with `url: (mem) => \`/dashboard/requests/${mem.get(RequestId.key)}\``
- **THEN** running it SHALL navigate to the URL produced by that function, called with the
  same `mem` passed into `act()`

### Requirement: A regular Block's page marks navigation methods as deprecated
Enforcement SHALL be soft by design - authors are never blocked from calling navigation
methods on a regular (non-Nav) Block, only warned. A regular Block's `act()` SHALL receive
its `page` argument typed as `ActionPage`: structurally identical to Playwright's `Page`
for every method, except `goto`, `reload`, `goBack`, and `goForward` SHALL be re-declared
under a `@deprecated` JSDoc tag naming `defineNavBlock` as the alternative. This SHALL NOT
change runtime behavior, SHALL NOT be a type error, and SHALL NOT cause `tsc --noEmit` (or
any build) to fail on existing code that already calls these methods from a regular Block.

#### Scenario: An editor shows a deprecation warning immediately, without any command
- **WHEN** an author writes `page.goto(...)` inside a regular (non-Nav) Block's `act()`
- **THEN** a TypeScript-aware editor SHALL show that call struck through with a hover
  message pointing at `defineNavBlock`, with no command run and no build step required

#### Scenario: Existing navigation calls keep compiling and running unchanged
- **WHEN** an existing Block (e.g. a frozen `zsign-all` reference Block) calls `page.goto`
  from inside a regular `act()`
- **THEN** `tsc --noEmit` SHALL still succeed
- **THEN** running that Block SHALL behave exactly as before this change

#### Scenario: Non-navigation methods are unaffected
- **WHEN** a regular Block's `act()` calls `page.locator(...)`, `.click()`, `.fill()`, or
  any `Page` method other than `goto`/`reload`/`goBack`/`goForward`
- **THEN** it SHALL typecheck and behave identically to calling it on the real `Page`,
  with no deprecation warning

### Requirement: waygraph check sweeps a whole project as a complementary check
`waygraph check <project>` SHALL walk every `*.block.ts` file under the target project
and, for each Block not built via `defineNavBlock`, SHALL scan that file's own source text
for `page.goto(`, `page.reload(`, or `page.goBack(`. On a match, it SHALL print a warning
naming the file and the Block. This SHALL be a warning only - it SHALL NOT fail the
process or change its exit code. This exists alongside the `ActionPage` deprecation above,
not instead of it: `check` covers contexts with no editor watching (CI, an autonomous
agent writing Block files without a language server, a one-shot audit of many files at
once), while the deprecation warning is the immediate, per-keystroke signal during
authoring.

#### Scenario: An action Block that navigates gets flagged
- **WHEN** a Block not built via `defineNavBlock` contains `page.goto(...)` in its own file
- **THEN** `waygraph check` SHALL print a warning naming that Block's file
- **THEN** `waygraph check`'s own process exit code SHALL remain `0`

#### Scenario: A NavBlock never triggers its own warning
- **WHEN** a Block is built via `defineNavBlock`
- **THEN** `waygraph check` SHALL NOT warn about it, regardless of its generated `act()`

#### Scenario: A clean action Block produces no warning
- **WHEN** a Block not built via `defineNavBlock` contains no `page.goto(`, `page.reload(`,
  or `page.goBack(` in its own file
- **THEN** `waygraph check` SHALL NOT warn about it

#### Scenario: Navigation hidden behind a shared helper is a known blind spot
- **WHEN** an action Block calls a helper function imported from another file, and that
  helper - not the Block's own file - contains `page.goto(...)`
- **THEN** `waygraph check` MAY NOT detect this; detection is scoped to the Block's own
  file's source text, not a transitive import graph. This is a documented limitation, not
  a defect.

### Requirement: check is opt-in and does not touch existing consumers
`waygraph check` SHALL be a new, separately-invoked CLI command, distinct from
`list`/`nav`/`validate`/`run`/`chain`. Running any existing command SHALL NOT run these
checks. Existing Blocks that mix navigation and action in one Block (e.g. the frozen
`zsign-all` reference Blocks) SHALL continue to work unchanged; `check` only ever produces
warnings about them, never errors.

#### Scenario: Existing consumers are unaffected until they opt in
- **WHEN** a project with pre-existing Blocks that call `page.goto` from a non-nav Block
  runs any of `list`/`nav`/`validate`/`run`/`chain`
- **THEN** nothing about those commands' behavior SHALL change
- **THEN** only an explicit `waygraph check` invocation SHALL surface any warning about them
