E2E architecture — zsign-app

Waygraph

A typed graph of reusable Blocks for driving a browser through E2E flows, in place of a flat pile of ad hoc helper functions. This is the reference for what's actually built and tested in @waygraph/core today - not the plan, the shipped thing.

Release beta, actively growing Proven against a live site (saucedemo.com) - not just fixtures Tests 64 in @waygraph/core, 5 end-to-end in project/saucedemo
A note on how this got built: the original design sketched Checkpoint, Block, act/observe/resolve/verify, MemPage, branch(), and spawnTab up front. Engine, defineFlow, and Flow did not - they emerged during implementation, once hand-nesting connect() calls and juggling raw terminals sets by hand got painful enough to need a name. Same with defineBlock/DefinedBlock and the whole discoverable-methods layer - that came from actually using the library and noticing free functions (withVerify(block, ...)) don't show up in autocomplete the way block.withVerify(...) does. This doc reflects the built thing, warts, corrected mistakes, and all - not a plan executed cleanly top to bottom.

01

Checkpoint & Block

A Checkpoint is identified solely by its string tag - a phantom marker, zero embedded data, always. checkpoint("LoggedIn") builds one (matches key()'s pattern for MemKey) instead of hand-typing { __state: "LoggedIn" } everywhere - that raw shape is banned from every call site in this codebase now, it exists in exactly one place: checkpoint()'s own one-line body.

A Block wraps one instruction. Its input and output are Checkpoints - connect(a, b) only typechecks when A's output tag equals B's input tag, so a flow is a chain the compiler rejects before Playwright ever opens a browser. Two different instructions reaching the same Checkpoint are interchangeable everywhere they're used.

core/types.tssettled
type Checkpoint<Tag extends string> = { readonly __state: Tag };
function checkpoint<Tag extends string>(tag: Tag): Checkpoint<Tag> { return { __state: tag }; }

interface Block<In extends Checkpoint<string>, Out extends Checkpoint<string>> {
  name: string;
  instruction: Instruction<In, Out, any>;
  next?(checkpoint: Out): Block<any, any> | null | undefined;     // set by branch()
  requires?: readonly MemKey<any>[];                          // checked by preflight()
  withVerify?(verify): Block<In, Out>;                       // optional - see section 03
  modVerify?(nameOrIndex, newCheck): Block<In, Out>;
  modVerifyAll?(patches): Block<In, Out>;
}
02

The instruction lifecycle

Most Blocks need only act and a one-line resolve. Add observe only once a Block genuinely branches - it's the only phase allowed to look at the DOM before a decision is made, or open a second tab. Add verify only once you want to confirm the reached state, not just classify it.

core/types.tssettled
interface Instruction<In, Out, Observed = void> {
  act(page: Page, input: In, mem: MemPage): Promise<void>;
  observe?(page: Page, mem: MemPage): Promise<Observed>;              // optional
  resolve(observed: Observed): Out | Promise<Out>;                     // mandatory, pure
  verify?: Trait[] | ((out: Out) => Trait[]);                          // optional, post-resolve
}
  • act - page, input, mem. Drives the browser only, this tab, nothing else.
  • observe - page, mem. Gathers evidence, runs assertions, writes memory, the only phase that can spawnTab-style open a second page (see section 04).
  • resolve - observed only. No page, no mem in its parameter list at all - not a lint rule, a missing parameter. Reproducible from its input alone.
  • verify - runs after resolve has already decided Out, never before, and can never redirect it - only confirm or fail loud. A function form ((out) => Trait[]) picks different checks per branch, since a failed login shouldn't be checked against "reached the dashboard".
03

Discoverable Block operations — newest layer

Free functions (withVerify(block, ...)) work, but they don't show up when you type LoginBlock. in an editor - you have to already know they exist. That's a real, correct complaint: util(object) discoverability is worse than object.util(), no autocomplete or LSP can fix it for you.

defineBlock() is the fix - a constructor that attaches withVerify/modVerify/modVerifyAll as real, bound methods. A raw object literal is still a perfectly valid Block (every low-level test fixture in this codebase is one) - it just won't have them attached. Their return type is DefinedBlock, not plain Block, so chaining (.withVerify(...).modVerify(...)) never needs a ! assertion.

project/saucedemo/src/blocks/login.block.tsreal usage
export const LoginBlock = defineBlock<Start, LoggedIn>({
  name: "login",
  requires: [LoginCreds.key],
  instruction: { act, resolve: () => checkpoint("LoggedIn"), verify: [Trait.url({ pathname: "/inventory.html" })] },
});

// derive a variant with zero verify - the QA "only care I navigated" case
const smokeLogin = LoginBlock.withVerify([]);

// tweak one existing check by name (or index), everything else untouched -
// the v1/v2/legacy-app case
const v2Login = LoginBlock.modVerify("url-matches", Trait.url({ pathname: "/dashboard.html" }));

withVerify vs. modVerify/modVerifyAll

withVerify(block, list) replaces the whole list wholesale - the only way to express "clear to empty" or go from zero verify to some. modVerify/ modVerifyAll only replace existing named entries (throwing loud if the name/index doesn't exist) - for tweaking one or several checks in a large list without restating the rest. modVerify is built on withVerify internally; removing withVerify was proposed and rejected once already - it would have broken both modVerify's own implementation and the empty-list case.

Addressing: by name (recommended - Trait.name already exists for exactly this), or by numeric index if you genuinely know the position. A positional parallel array with null placeholders for "skip this Block" was considered and explicitly rejected - it's the same fragility as a chained-method, class-based Block: insert or reorder something and it silently retargets the wrong thing.

The correctness trap this layer had to solve: a Block's attached methods close over the shape it had when they were attached. Call .withVerify() on a Block that branch() added routing to afterward, and a naive implementation would silently drop that routing - the stale closure never knew next existed. Every function that returns a new Block (branch, withVerify, modVerify) strips old methods and rebuilds through defineBlock before returning, specifically to close this hole. Proven by a dedicated test, not just reasoned about: a branch()'d Block's routing survives a .withVerify() call afterward.
04

The engine, Start/End

Start and End aren't instructions anyone writes - they're rules the engine enforces. Start creates the tab before the first Block runs; End is whichever Checkpoint tag has no further routing, and reaching one closes the tab. The terminal Checkpoint is the graph's actual return value, not discarded - pass/fail/skip falls out of "which tag you landed on".

core/engine.tssettled
async function runGraph<TOut>(entry, terminals, context, mem, maxSteps = 5000): Promise<TOut> {
  preflight(mem, entry);                         // fails in ms, before a tab opens - see section 07
  const page = await context.newPage();
  try {
    let current = entry, input = checkpoint("__start__"), steps = 0;
    for (;;) {
      if (++steps > maxSteps) throw new Error(`exceeded ${maxSteps} steps`);
      await current.instruction.act(page, input, mem);
      const observed = current.instruction.observe ? await current.instruction.observe(page, mem) : undefined;
      const out = await current.instruction.resolve(observed);
      await runVerify(current.instruction.verify, out, page, mem, current.name);
      const next = current.next?.(out);
      if (!next) { if (terminals && !terminals.has(out.__state)) throw new Error("not a registered terminal"); return out; }
      current = next; input = out;
    }
  } finally { await page.close(); }
}

spawnTab, honestly: the original plan called for a distinct spawnTab primitive for a second browser tab. It never got built as such - what's actually shipped is that observe is the only phase allowed to reach page.context() and open a second page, calling runGraph again recursively for a sub-flow, sharing the same MemPage. No dedicated spawnTab function exists yet; this remains genuinely open (see section 10), not secretly done under a different name.

05

Engine, Flow, EngineConfig

Defining a flow as hand-nested connect() calls plus a manually-tracked terminals set got painful fast - this is the part of the design that didn't exist on paper first. Engine.defineFlow([start, ...blocks, end]) composes the array via connect() internally (no new chaining logic to trust) and returns a Flow with no terminals to manage - a linear chain has exactly one reachable outcome by construction.

project/saucedemo/src/flows/checkout.flow.tsreal usage
const engine = new Engine({ headless: false, slowMo: 250 });   // launches & owns its own browser

export const checkoutFlow = engine.defineFlow([
  start, LoginBlock, AddToCartBlock, CheckoutInfoBlock, FinishOrderBlock, end,
]);

// tests/checkout-flow.spec.ts
await checkoutFlow.run(mem);                          // no context - Engine launches its own
await checkoutFlow.run(mem, { headless: true });        // per-call override, e.g. for CI
await checkoutFlow.run(playwrightContext, mem);       // or share an existing context - config ignored
  • EngineConfig - headless, browserName (chromium/firefox/webkit), slowMo. Only meaningful when the Engine launches its own browser (run(mem)); ignored by run(context, mem), since that browser's already running under Playwright's own config.
  • Per-call override merges over the Engine's constructor config, per key - one module-level Flow, imported by many specs, doesn't force every caller into the same settings.
  • slowMo exists specifically so a human can watch a run happen - proven with a timing test (not just accepted-and-trusted), which flaked once on a too-tight margin against real system noise and got a wider margin, not a retry loop.

Patching a Flow's Blocks after composition — newest layer

withVerify/modVerify (section 03) only reach a Block you still hold a reference to. Once Blocks are composed into a Flow, a spec that only imports the finished checkoutFlow had no way back in - override one Block's confirmation for just this test, and the only options were editing checkout.flow.ts itself (changes it for every caller) or hand-rebuilding the whole Block list inline. Real gap, closed the same way withVerify/branch() already work: decorate, don't mutate, return a new Flow.

project/saucedemo/tests/flow-block-verify.spec.tsreal usage, live site
// Preferred: the actual Block reference - typo-proof, refactor-safe,
// jump-to-definition works. A plain string name is still accepted too.
const patched = checkoutFlow.withBlockVerify(LoginBlock, [
  Trait.url({ pathname: "/inventory.html" }),
  Trait.visible(".inventory_list"),
]);
await patched.run(mem);                          // checkoutFlow itself is untouched

checkoutFlow.modBlockVerify("login", 0, { name: "...", check: async () => false });
Why resolution is by .name, not by object identity, even when you pass a reference: a patch returns a new Block for that slot, so the original reference you passed in is no longer === anything inside the result. Addressing by .name underneath - the Block's already-established stable identity in this codebase - means the same reference still resolves correctly even after an earlier patch already swapped that slot. Proven with a dedicated test that patches twice in a row via the same original reference.
06

branch(), self-loops, maxSteps

Real flows branch (login succeeds vs. fails) and sometimes repeat (poll until an email arrives, send N messages to test a rate limit). branch() only attaches next to a Block - it never touches act/observe/ resolve/verify, so everything already proven about those phases still holds for a routed Block.

core/engine.tssettled
branch(SendChatMessage, {
  CanSend: SendChatMessage,        // self-loop - branch() already permits routing to itself
  RateLimited: null,             // null = terminal, stop here
});

No separate "repeat" primitive exists - a self-loop is just a route pointing back at its own Block, and maxSteps (default 5000, on runGraph) is the one genuinely new safety net, since nothing before branch() existed could loop at all. branch()'s return type is deliberately loose (Block<In, any>) - a route can lead anywhere, including back through itself, so there's no fixed Out type to express; state expected outcomes to runGraph via terminals instead, where that's still needed.

07

Trait, verify, preflight

Trait factories

Every Block writing its own inline { name, check } object is not "using Traits" - it's writing assertions with extra ceremony. A small reusable factory library replaces that, reachable two ways - as free functions, or off Trait. itself for autocomplete discoverability (same functions, same objects, just findable by typing Trait. without needing to already know urlMatches exists):

core/trait.tssettled
Trait.url(pattern: URLPatternInit): Trait   // { pathname, hostname, search, hash, ... }
Trait.text(selector, expected): Trait       // element text content equals
Trait.visible(selector): Trait              // waits for visibility

Trait.url takes a structured URLPatternInit - the real, standard URLPattern Web API shape - not a hand-written regex. Whichever components you leave out default to "match anything", so Trait.url({ pathname: "/inventory.html" }) already ignores whatever query params a hybrid SPA tacks on (a selected tab, a session id) - no separate flag needed for that, and verified directly (node -e, not assumed) before committing to it. An earlier pass added a bespoke { ignoreParams: true } boolean on top of raw regex first; it got replaced entirely once the regex-wrapper approach itself was called out as adding ceremony without adding real structure over what Playwright's own waitForURL already does.

A real type-safety hole this pass also caught: this project had no @types/node installed, and URL/URLPattern aren't in TypeScript's own bundled lib - so under skipLibCheck, the predicate parameter in an earlier Trait.url implementation was silently typed any. tsc --noEmit reported zero errors while genuinely checking nothing on that parameter. Caught with a deliberate @ts-expect-error probe (an "unused directive" report means no error was actually there), not noticed by inspection. Fixed by adding @types/node to both packages that need it.

preflight / requires

A Block declares requires: [SomeKey]; connect() unions requires from both Blocks into the composed one, so a defineFlow-built chain's entry ends up carrying every constituent Block's requirements for free. preflight() checks all of them at once (naming every missing key together, not one-by-one) and runGraph calls it automatically, before context.newPage() - proven against the real timing, not assumed: a missing credential fails in single-digit milliseconds against a full multi-second real run.

Known limit, stated plainly: this only sees Blocks reachable through connect()'s static composition - a Block only reachable via branch() routing isn't preflighted, since which route fires is a runtime decision that hasn't happened yet.

08

Typed memory

The key carries the type, not the store. MemKey<T> is identity-keyed (two keys can share a debug name and never collide); reading before writing throws immediately, naming the key.

core/mem-page.tssettled
mem.set(UsernameKey, "standard_user");
mem.setAll([UsernameKey, "..."], [PasswordKey, "..."]);         // several keys, one call

// keyGroup: one key holding a whole shaped value, not two primitive keys
const LoginCreds = keyGroup<{ username: string; password: string }>("creds");
mem.set(LoginCreds({ username: "...", password: "..." }));         // set() also takes a pair directly - no "All" for just one

Modular layout, proven live

project/saucedemo/ is the real, working reference - three flows, all passing against the actual live site, not a mock:

project/saucedemo/src/ states/ checkout.states.ts (Checkpoints) · checkout.mem-keys.ts (LoginCreds) blocks/ login, add-to-cart, checkout-info, finish-order (all via defineBlock) flows/ checkout.flow.ts (strict, non-headless, slowMo) · smoke.flow.ts (.withVerify([]) reuse) tests/ checkout-flow.spec.ts full flow, live site preflight.spec.ts missing creds fail in ms, no browser touched smoke-flow.spec.ts same Blocks as checkout, navigation-only confirmation

smoke.flow.ts is the concrete proof the whole "discoverable operations" layer (section 03) is worth what it cost: it reuses LoginBlock and AddToCartBlock exactly as authored for the strict flow, with .withVerify([]) stripping confirmation for a QA "did I navigate this far" check - zero duplicated Block logic between the strict and smoke variants.
